# アーキテクチャ（基本設計）

## 役割と依存

```text
URDF + STL meshes
      |
      v
  RobotModel ----> Kinematics (FK, IK, Jacobian)
       \----------> CollisionChecker
                            ^
SwiftViewer <--> SimulationController --> Kinematics
```

### RobotModel
URDFのパース、関節名・順序・制限、TCPリンク、衝突形状を管理し、RTB-Pのロボットオブジェクトを公開する。

### Kinematics
生成済みモデルを参照し、`fk(q)`、方向拘束付き`ik(xyz, direction, q0)`、ヤコビアン計算、TCP誤差検証を担当。URDFファイルは直接読まない。

### CollisionChecker
関節角`q`を受けて自己干渉・障害物干渉を判定。初期実装ではライブラリ側の内部リンク姿勢更新に任せ、計算の共有は性能上の必要が出てから検討。RTB-PバージョンとURDF collision形状の対応は要検証。

### SimulationController
IK→FK検証→衝突判定→採否判断を統括。IK失敗・目標誤差超過・関節制限違反・衝突時には現姿勢を維持して失敗理由を返す。

### SwiftViewer
3Dモデル、目標位置とTCPの可視化、XYZスライダー。計算や採否判断はControllerに委譲。

## SO-101の重要な条件

6つ目の駆動軸は通常の手首回転ではなくグリッパ開閉軸で、可動爪先端をTCPに取るとその角度がTCP位置に影響する。一般的な6自由度アームと同様に任意の位置姿勢を実現できるわけではない。

TCPのローカル+Zを爪先方向とする案。下向き方向`[0,0,-1]`はベース+Zが鉛直上向きという条件付き。位置XYZ＋方向の5拘束でIKを解き、鉛直軸周りは自由にする。

## フィージビリティと衝突

1. IKで候補関節角を生成
2. FKでTCP位置・方向の誤差確認、および関節制限確認
3. CollisionCheckerで自己衝突・障害物衝突確認
4. Controllerで姿勢採用・却下

FKを先に全リンクについて明示的に行う必要があるかは衝突ライブラリ次第。候補方式は (A) 全リンクFKを渡す、(B) `q`だけを渡して内部FKに任せる、(C) 共通のリンク姿勢を共有する、の3つ。初期構成では(B)を採用する。

## 未決事項・要検証

- SO-101公式URDFのリンク名、第6軸のジョイント形式、TCPまでのチェーン
- STL座標系の軸方向とURDFリンク座標の合わせ込み
- TCPの実寸オフセットと工具姿勢
- RTB-PでのURDF読込・Swift描画・第6軸を含むIKの可否
- IKの最適化アルゴリズム、ヤコビアン、収束と複数解
- 衝突計算の依存ライブラリ・APIとURDFメッシュの扱い
- 関節空間経路補間と途中の衝突検証

この文書は設計段階の整理であり、実装済み・実機での動作確認済みとは主張しない。
